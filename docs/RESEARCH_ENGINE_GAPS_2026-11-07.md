# Engine gaps research for lemonade-burn (2026-11-07)

Method: ~16 web searches, search-result summaries only (no deep page reads). Many forum/Reddit items carry no clear date; marked "undated". Anything I did not find is marked NOT FOUND.

## Ranked: what lemonade-burn should do next
1. **Fix the P100 matmul path first (fp16x2 dequant, no int8 assumption).** The P100 (GP100, sm_60) has no DP4A/DP2A (those are GP102/104/106 only) but has paired fp16: ~19 TFLOPS via half2 ([NVIDIA CUDA 8 blog](https://developer.nvidia.com/blog/mixed-precision-programming-cuda-8), [Pascal tuning guide](https://docs.nvidia.com/cuda/archive/8.0/pascal-tuning-guide/index.html), [TechPowerUp P100](https://techpowerup.com/gpudb/2888/tesla-p100), all 2016-era docs). Peak needs operands stored as half2. A Q4_0 kernel that unpacks nibbles to half2 and FMAs is the natural route. Your 18 vs 66 tok/s gap is a kernel problem, not an architecture problem. Also: every ecosystem tool treats 4-bit as dequant-to-fp16 on cards lacking the mixed-precision instruction ([ai-muninn 2080 Ti test](https://ai-muninn.com/en/blog/why-4bit-isnt-faster-on-2080ti), undated), so you are not behind a better trick; you are behind a tuned one. NOT FOUND: any published dp4a-free sm_60 int4 kernel write-up or benchmark. Read llama.cpp's own sm_60 path (it is what gets 66) as the reference.
2. **Placement probe + auto-fit as a first-class, measured step.** llama.cpp's `--fit` (lowers context, then moves tensors to RAM, dense before MoE, default reserve 1024 MiB) is the bar ([llama.cpp discussion 18049](https://gh.r-mj.com/ggml-org/llama.cpp/discussions/18049)). Users still report it overshoots one GPU and OOMs, and tune `-ngl`/`--n-cpu-moe` by hand ([Reddit, May 2026](https://reddit.sentinel-team.org/posts/1trh4p9/snapshots/2026-05-30T00%3A45%3A07.677242Z); [Reddit, Apr 2026](https://reddit.sentinel-team.org/posts/1srvqar/snapshots/2026-04-25T00%3A46%3A56.728262Z)). It fits by size, not by measured speed. Do it by measured tok/s per tensor group, written to the manifest/state.
3. **Fleet-level placement across machines (the open niche).** vLLM: forum answers say no native heterogeneous GPUs in one instance ([vLLM forum](https://discuss.vllm.ai/t/how-to-run-a-model-use-heterogeneous-gpus/1360), [mixed GPU](https://discuss.vllm.ai/t/mixed-gpu-support/2506), undated, community answers not docs). Research exists (HexGen, Zorse: [Zorse, Jul 2025](https://arxiv.org/pdf/2507.10392)) but no product. llama.cpp RPC splits by memory and "loses speed as you add nodes" ([2026 guide](https://fungies.io/multi-node-local-llm-inference-guide-2026)); large-model RPC load hangs above ~100 GiB ([issue 19745](https://github.com/ggml-org/llama.cpp/issues/19745), 2026, workaround `-dio`); tensor-parallel over RPC is only a request ([issue 13083](https://github.com/ggml-org/llama.cpp/issues/13083)). A tuner using your RoCE link, per-card measured speed and per-expert hit rates has no equivalent.
4. **Expert tiering (VRAM / RAM / Optane / SSD) driven by observed routing.** ktransformers (SOSP 2025) is CPU+GPU only, best at low concurrency, fastest path needs AMX CPUs, and inherits SGLang's model coverage ([paper page](https://madsys.cs.tsinghua.edu.cn/publication/ktransformers-unleashing-the-full-potential-of-cpu/gpu-hybrid-inference-for-moe-models/); [OSDI26 paper](https://www.usenix.org/system/files/osdi26-wang-wenxin.pdf): prior systems <20 tok/s decode, poor under concurrency). An unmerged llama.cpp PR adds an auto-fit "expert hot store" ([PR 26563](https://github.com/ggml-org/llama.cpp/pull/26563), 2026) - someone is moving here; check it before building. PowerInfer-2 has the hot/cold cache idea for dense neurons on flash, with I/O still the cost; no MoE expert cache design found ([arXiv 2406.06282](https://arxiv.org/pdf/2406.06282), 2024). SSD tier is not shipped by any mainstream engine that I found.
5. **Dequant lab = per-card quant recommendation, built on existing tools.** See section 3. Nobody ships the recommender; build it as a measured table (card x quant -> tok/s, KL) rather than a heuristic.
6. **Polaris/Vulkan: accept dequant cost, test fp32/fp16 reality.** RX 580 reports show fp16: 0, int dot: 0, matrix cores: none ([Reddit, Mar 2026](https://reddit.sentinel-team.org/posts/1rtab9m/snapshots/2026-03-16T20%3A46%3A16.316967Z)); q8_0 KV was ~22% slower than f16 there ([llama.cpp discussion 23109](https://github.com/ggml-org/llama.cpp/discussions/23109)). Low priority; small models only.
7. **Do not build the Movidius helper** (section 5).

## 1. What others say is missing or painful

## 2. Auto-tuning
- llama.cpp: tunes layer count, context, tensor placement to fit VRAM (size-based; see item 2). Does not measure speed; no cross-machine view.
- ktransformers: fixed CPU/GPU split by design (attention/shared on GPU, experts on CPU); AMX-optimised ([SOSP25](https://madsys.cs.tsinghua.edu.cn/publication/ktransformers-unleashing-the-full-potential-of-cpu/gpu-hybrid-inference-for-moe-models/)). A Dec 2025 paper reports >=2 CPU cores beat plain layer offload ([arXiv 2512.16473](https://arxiv.org/pdf/2512.16473)).
- exllama calibration, vLLM autotune, TVM/Triton: I did not retrieve sources this pass. UNKNOWN from this research (Triton/TVM autotune kernel tile sizes per GPU from general knowledge only).
- Missing for a fleet tuner: a per-card measured kernel table; per-node bandwidth (PCIe, RoCE, NVMe, Optane) as inputs; expert-hotness from routing traces; a solver that outputs placement for N machines; re-run on hardware change; output as state (JSON) an agent can edit. None found in any engine.

## 3. Dequant lab
- Tools: llama-quantize with `--imatrix`, per-tensor `--include-weights`; whole model loaded in RAM, memory and disk need are equal; `--allow-requantize` degrades quality, start from bf16 ([quantize README](https://docs.rs/crate/llama-crab-sys/latest/source/llama.cpp/tools/quantize/README.md)). ik_llama's `--individual-tensors` quantizes bf16 shards one tensor at a time ([Thireus Kimi K2.5 card](https://huggingface.co/Thireus/Kimi-K2.5-THIREUS-Q4_0-SPECIAL_SPLIT)), which cuts peak RAM; exact figure NOT FOUND.
- Unsloth Dynamic 2.0: per-layer quant type chosen per model, all architectures, own calibration set, KL-divergence evaluation ([docs](https://docs.unsloth.ai/basics/unsloth-dynamic-2.0-ggufs)).
- QAD: Liquid LFM2.5 Q4_0 (Aug 2026) closes 48-73% of the bf16-to-Q4_0 gap, smallest models best, same GGUF Q4_0 format so it runs in any Q4_0 kernel ([Liquid blog](https://liquid.ai/blog/qad), vendor numbers). Only 230M-2.6B; no MoE QAD found.
- Cost (my arithmetic, not sourced): bf16 = 2 bytes/param. 24B = ~48 GB, 120B = ~240 GB, 1T = ~2 TB on disk; full-load quantize needs about that much RAM (so 1T needs per-tensor streaming). Output Q4 about 0.56 bytes/param. Wall-clock times: NOT FOUND. Imatrix generation needs a forward pass of the bf16 model over calibration text, so it needs the hardware to run the model once.
- Automatic "pick the right quant for your cards": NOT FOUND. Closest: manual guidance and Unsloth/ubergarm per-model quant ladders ([ubergarm Kimi-K2.6](https://huggingface.co/ubergarm/Kimi-K2.6-GGUF)).
- Practical for you: Q4_0 stays; the lab's job is picking mixed per-tensor types (e.g. keep attention higher, experts Q4) and measuring tok/s plus KL per card.

## 4. Old hardware
- P100: dequant to half2 is the only route (item 1). NOT FOUND: a dp4a-free sm_60 benchmark vs RTX on the same quant. Estimate (unsourced): decode is bandwidth-bound; P100 HBM2 732 GB/s from spec sheets vs RTX 2060 ~336 GB/s, so P100 should not lose decode to a 2060; prefill compute favours Turing tensor cores.
- Marlin-style kernels need tensor-core mma (sm_75+ via new PR, older notes say 8.0); useless on sm_60. vLLM GPTQ min capability reported 60, AWQ/FP8 75 ([particula](https://particula.tech/blog/awq-vs-gptq-vs-fp8-quantization-choice), secondary).
- Polaris: no int dot, no fp16, no cooperative matrix (item 6). 16-27 tok/s on 4B Q4-Q6 models reported.

## 5. Movidius NCS1
Vendor: ~100 GFLOPS fp16, ~1 W, USB 3.0, linear scaling to 4 sticks claimed ([AnandTech](https://www.anandtech.com/show/11649), [Tom's Hardware](https://www.tomshardware.com/news/movidius-launches-neural-compute-stick,35047.html), 2017). Arithmetic: P100 fp16 ~19,000 GFLOPS, so the stick is ~0.5%; four sticks ~2%. USB 3.0 5 Gb/s = ~0.5 GB/s best case versus 732 GB/s HBM, ~1/1400. A 2B-active Q4 token reads ~1 GB of weights: 2 s per token if streamed over USB; compute is ~4 GFLOP/token = 40 ms on the stick but only if weights already live in its memory (a few hundred MB, my recollection, unverified). Verdict: no. The stick cannot hold experts, cannot feed the GPU, and the GPU's missing int8 is solved by half2 on-card. Your separate Ghidra/bare-metal NCS work stands as research, not as a helper.
